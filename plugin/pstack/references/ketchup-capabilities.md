# Catch-up capability binding

Use this binding for [ketchup](../skills/pstack-ketchup/SKILL.md), under the [shared compatibility contract](compatibility.md). Packaging supplies no history, forge, worker-control, screenshot or chart tool. Bind only exposed, permitted read operations after inspecting their schemas. The [capability evidence](../qualification/capabilities.md) C3/C4 and C7–C9 supports the conditional invocation/history/control contracts, not guaranteed recipient tools.

## Conversation boundary

Use supplied current-conversation messages when their authorship and ordering identify the user's last pre-invocation message and the subsequent work. Compacted or summary-only context cannot establish a missing boundary, complete earlier pending-action inventory or original execution. If needed, follow [scoped history](history.md) to bind the host's current-chat reader and page only this conversation. Distinguish human messages from notifications and delegate reports by actual record types, not wording. Read enough prior context to find still-unresolved user actions. Report missing/truncated history and the exact missing boundary or coverage; do not claim a complete catch-up until supplied.

## Current artifact state

For each touched PR/run bind the exposed forge read operation (or an already available authenticated read-only CLI) to its known identity and inspect state/check fields. For agents use a current status/list/wait-snapshot operation, not a send, resume, interrupt or spawn. A report or transcript timestamp is not liveness evidence. Map response identities back to recognizable task/PR/branch names. A zero-timeout snapshot may be used only if supported; never start a watcher or job. Read local artifacts only within the conversation's scope. Record evidence time and distinguish current observations from earlier reports. For numbers, retain source values, units and derivation; incomplete inputs mean unknown. Unavailable readers leave individual states not checked and scope limits explicit.

Examples of host bindings, only when actually exposed with these semantics: `mcp__codex_app__read_thread` returns recent status/turn summaries with cursors and optional truncated outputs, so it cannot alone establish full execution or a missing exact message boundary; `mcp__codex_app__wait_threads` with `timeoutMs: 0` reads a compact current snapshot for known touched Codex chat IDs. `collaboration.list_agents` can read the current agent tree where that API exists. These names are candidates to inspect, never a promise that packaging provides them. An already available `gh pr view` or `gh run view` can read a known touched forge artifact under existing authentication. Bind the actual response fields and identities before reporting state.

## Reply visuals

Reuse available, relevant captured screenshots/video and verify their artifact identity and time before presenting them as observed changes. Any fresh capture must be a permitted read-only observation of an already available surface, through its exposed API and host restrictions. This workflow does not invoke verification-control setup, launch a browser/app/server, navigate to manufacture evidence, or install tooling. Missing capture is “No screenshot yet.”

For progress, structures and option comparisons, use Mermaid only when the recipient response renderer supports rendered diagrams. Otherwise bind an available diagram/chart tool or generate a local reply-only SVG/PNG with already available tooling from verified facts. Confirm the host can display the resulting artifact; a code fence of unrendered diagram source is not a picture. Numerical charts retain units and known values; uncertain option costs remain unknown. Generated visuals may represent facts and choices, never pretend to be captured screens. A companion visualization skill is optional only if actually present and usable within this read-only scope.

If no usable visual channel exists, identify the required progress/action visual as blocked. A partial text report must state its limitation and cannot count as full ketchup completion. Likewise, an unavailable history boundary blocks the complete interval claim. These fallbacks disclose unsupported requirements rather than relax them. Read-only catch-up ends after the reply, even if the remaining task is authorized elsewhere.
