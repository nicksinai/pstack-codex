# Skill authoring companion

This is the portable counterpart for pstack's calls to Cursor's built-in create-skill. Read the recipient's actually available Codex `skill-creator` instructions through the host skill catalog/path when present. Do not assume a callable Skill API, install a creator, or edit a global skill to obtain it. The built-in Cursor companion's full source was unavailable in the pinned public upstream; exact fidelity to its hidden behavior is unresolved. This adapter preserves the authoring obligations visible in pstack plus Codex's documented skill structure. It supplies a bounded authoring path when no recipient creator is exposed.

## Author and validate

1. Identify the approved task, target skill, exact update scope, representative requests and intended invocation policy. Read the existing skill and relevant local authoring instructions. Preserve sections, metadata, dependencies, assets and policy that the user has not contradicted. Check whether an existing skill already owns the workflow before proposing a new one. Reflection Accepted rows require explicit row approval before editing.
2. Draft instructions that change decisions, with a clear completion criterion. Keep reusable workflow steps in SKILL.md, conditional detail in linked references, executable helpers only when needed, and output assets separate. Delegate by resolvable path rather than duplicate another skill. Point to structural sources such as types/configuration instead of caching their current values. When in doubt, delete prose that changes no decision; explain only confusing rules. A recurring uncaptured workflow merits a proposal for a new skill, not automatic creation.
3. Use a lowercase kebab name under 64 characters and matching directory; required frontmatter is `name` and a brief discriminating `description` as one valid YAML scalar. Preserve optional supported metadata. For new pstack-derived explicitly invoked skills use `agents/openai.yaml` policy `allow_implicit_invocation: false`; preserve existing third-party policy unless the user requests a change. Confirm the actual host discovery root and selector spelling. A policy flag and a useful description serve separate purposes.
4. For structural skills, use appropriate representative cases to check meaningful outputs/invariants and iterate on demonstrated failures, respecting the user's verification preferences. Subjective personal modes use the user's draft feedback rather than a benchmark suite. Always check frontmatter, name/directory correspondence, every referenced local file and cross-skill target, unfinished placeholders and helper prerequisites. Run the recipient creator's SKILL.md validator on every touched skill when shipped; inspect its real command/path and dependencies first. If missing or unusable, report the precise limit and do direct checks. Do not install dependencies just to conceal an unavailable optional validator.
5. Show the reviewable draft/diff, gather feedback and iterate. Apply [unslop](../skills/pstack-unslop/SKILL.md). Separate approved/applied/delivered state. A subjective draft is done when the user accepts its fit and structural checks are complete; do not claim user acceptance from silence.
6. For repository-managed changes follow [PR delivery](pr-delivery.md), including isolation, review and the user's delivery limits. Personal/global target application follows the user's actual authorized destination; draft preparation never implies publication, installation, overwrite or messaging authority. Keep personal data out of a shareable bundle.

## Description optimization

For `tune description` routings, read the target and the actual missed-trigger evidence. Distinguish a weak description from intentional explicit-only policy or catalog omission. Preserve policy unless changed explicitly. Collect representative should-trigger and should-not-trigger requests, sharpen the front-loaded trigger branches and discriminating boundary, and iterate using available host evaluation only when useful/authorized. Report source-only assessment versus observed trigger outcomes separately. If host evaluation is unavailable, leave accuracy conditional rather than invent a benchmark result. Avoid extending the skill's task scope to make it appear more discoverable.

## Recipient help

Invoke the explicit reflect entry for active-session proposed improvements, or automate-me to draft/update working conventions. Reflection presents all Accepted/Rejected/Backlog findings and waits for Accepted-row approval. Automate-me asks about existing modes, mines only the agreed workspace/window, shows an iterative draft and delivers under the configured repository/personal boundary. Neither installation nor these entrypoints authorizes automatic personal configuration changes. Missing delegation, history, tracker, forge or validator access is named at its affected step; preserve usable authorized work without claiming that step succeeded.
