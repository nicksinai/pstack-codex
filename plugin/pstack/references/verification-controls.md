# Real-app verification control contract

Use this contract for prototype observations, pixel parity, generated project verification, maintenance live passes and shipping verification. It supplies instructions and binding rules, not a universal Codex control API. Actual local execution, tools, credentials, platform and app availability are prerequisites. A missing prerequisite leaves the affected proof blocked; source inspection, worker assurances and rendered mockups do not replace a required live pass.

## Discover and bind

1. Identify the user's actual surface and repository startup instructions. Inspect existing app skill/harness first; preserve its discovery and invocation conventions. Read [UI control](control-ui.md) for web/Electron/browser interaction or [terminal control](control-cli.md) for CLI/TUI. For HTTP services, inspect the actual route/auth contract and use an available HTTP client against the real running service. For mobile, desktop-native or library workflows, use a supported existing platform harness or native entrypoint with observable output; browser support alone does not establish control of those surfaces.
2. Inspect the exposed tool schemas, executable availability and installed project dependencies. Record the real launch/readiness, doctor, observe, action, state-wait, evidence and teardown operations with their arguments. Prefer the repo's harness, then an available host control surface, then a temporary local harness using already available dependencies. Never invent a callable Skill tool, assume this research chat's tools ship with the plugin, or add a project browser dependency merely for a probe unless requested.
3. Verify target identity before acting: checkout and build revision, URL/app marker or CLI command, working directory, data/profile path, authentication and owned process/session. If selection is ambiguous, list matching identities and resolve the target instead of guessing by tab order. Scope credentials and user data to the authorized app; use disposable local state where feasible.
4. Choose an evidence location that survives teardown. Record run ID, artifact names and sensitive-data permission. A proof names the action, resulting state and required side effects with exact app/revision/environment. Existing production boundaries may isolate external services, but test-only setters/endpoints and mocks are not substitutes for the real user path. Inspect dry-run effects directly; a name does not establish absence of writes/network.

## Ownership and failure

Use the [delegation resource ledger](delegation.md): one named owner per app instance, port, debug endpoint, profile/tab/session, data directory and artifact directory. Give concurrent writers independent reservations where supported. Otherwise serialize the live surface, even across separate worktrees. Read-only feature readers never drive; verification maintenance's coordinator owns all live interactions. Record borrowed versus run-owned instances. Clean borrowed-instance residue without terminating the borrowed instance. Runtime ownership is explicit instruction, not OS isolation.

Run doctor before the first drive, on each fresh CLI session and after any surprising/failed drive. If doctor cannot observe a wedged UI state, reset to a known state or relaunch. A skill-drift doctor fix gets one retry after restarting only what the fix invalidated. Preserve already captured evidence across every cleanup; check the named paths afterward. Clean failed-iteration residue, sessions and descendants as well as successful runs. Final teardown follows the last drive/re-proof. Terminate only verified run-owned identities, with error/timeout cleanup, and confirm exit; never kill by process name.

If a feature cannot be reached, capture the attempted route plus concrete unmet auth/entitlement/OS/external-state prerequisite. `verified-unreachable` reports that prerequisite, not a successful feature proof. Missing prerequisite documentation is drift. Missing tools or unobserved behavior remain blocked. Report product regressions separately from verification-doc/harness corrections; maintenance cannot repair product code or change the map merely to hide a regression.

## Generated project skills and delivery

The [generator](../skills/pstack-create-verification-skill/SKILL.md) writes actual discovered commands, selectors, readiness and evidence/cleanup paths into the recipient's project skill. Preserve its six required sections and maintained feature-map shape. A newly generated skill is a draft until its own launch/doctor/one-feature/evidence/cleanup sequence has run and proof survives cleanup. This live product gate remains mandatory even though qualification of this port is source-backed.

The [maintenance workflow](../skills/pstack-maintain-verification-skill/SKILL.md) requires source coverage and live exercise of every mapped feature, with clean/changed/blocked outcomes, no product-code edits and at most one PR of re-proven corrections. A source-clean wave cannot skip live coverage. Use [PR delivery](pr-delivery.md) only for the relevant changed deliverable under actual authority. A throwaway prototype instead ends in a decision and scratch artifact. Pixel parity uses a frozen baseline/harness and zero image diff; tool absence or a nonzero delta cannot be called parity.

## Capability evidence and limits

[Codex skills documentation](https://developers.openai.com/codex/skills) supports project `.agents/skills` storage, frontmatter and optional invocation metadata; it does not install the app-specific control executable. [Codex subagents documentation](https://developers.openai.com/codex/subagents) supports delegated source readers under actual host limits; it does not isolate running apps or enforce read-only instructions as a sandbox. The pinned [UI companion](https://github.com/cursor/plugins/blob/d0ef80d86795816da932a153458c5dbe192d294e/cursor-team-kit/skills/control-ui/SKILL.md) and [CLI companion](https://github.com/cursor/plugins/blob/d0ef80d86795816da932a153458c5dbe192d294e/cursor-team-kit/skills/control-cli/SKILL.md) establish source workflow requirements and example harness recipes, not universal Codex recipient capabilities. Tool-schema inspection and app execution establish a recipient's actual binding; until then browser/PTY, image-diff, auth and live-result claims are conditional.
