# Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

Read [delegation](../references/delegation.md), [PR delivery](../references/pr-delivery.md), [program state](../references/orchestration.md) and [continuation/recovery](../references/continuation.md) before starting. Bind actual host spawn/result/wait/stop controls and validated GPT roles; local workers replace cloud agents. Each writer gets an explicit isolated checkout, branch, base SHA and runtime resource reservation. These playbooks authorize scoped delegation when explicitly selected; installation alone supplies no task or merge authority. Independent GPT lanes lack upstream provider diversity.

Keep a recipient-private program store and invocation/checkpoint record using the shared contracts. Record the mode, queue, operator-owned items, explicit go/stop and delivery limits, owner and child IDs, exact current branches/heads/bases, findings, verdict receipts, countersigns, audit cadence, owned processes and next action. Program ledgers use exact-head identity. Shipping's narrow patch-ID retention can preserve specific lane evidence, but record the new head and recheck current CI/mergeability; it never turns a stale ledger row into a current-head pass. No PR merges merely because a helper labels it verified.


1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program through PR delivery, using supported built-in PR operations where the host requires them. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One isolated local owner per PR owns build, the first push, a ready PR, self-proof on the real artifact (the [prove-it-works principle](../skills/pstack-principle-prove-it-works/SKILL.md)), skeptical Bugbot triage per [Bugbot triage](../references/bugbot-triage.md), a slop-strip ([deslop](../skills/pstack-deslop/SKILL.md)), [no-comments](../skills/pstack-no-comments/SKILL.md), a rebase onto current trunk, the babysit loop to green ([Babysit](babysit.md)), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per [show-me-your-work](../skills/pstack-show-me-your-work/SKILL.md), pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and [no-comments](../skills/pstack-no-comments/SKILL.md), it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. Honor the PR delivery authority limits; a missing required push grant parks that action rather than bypassing it. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, fan out parallel independent verifiers per [swarm](../skills/pstack-swarm/SKILL.md) and aggregate to one verdict. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with [terminal control](../references/control-cli.md) or [UI control](../references/control-ui.md), or a named real-surface driver where neither applies, with actual supported tools). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in [Shipping](shipping.md).
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. Once that head is green and its patch-id matches the verdict's under the patch-id rule in [Shipping](shipping.md), a later trunk move does not force another rebase. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also check that no path in `git diff --name-only $(git merge-base HEAD origin/main) origin/main` is a path the PR changes or a path that decides which CI runs for it, such as the repo's CI config paths. If either check fails, rebase again, report the new head SHA, wait for CI to pass on it, and repeat these checks. A new head voids the verdict unless the patch-id is unchanged. The owner squash-merges its own PR through the resolved forge and returns. A fresh owner picks up the next self-contained item from the queue, per the shared delegation contract. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. On the operator's go, bind one actual hourly active-session audit wait using the continuation contract; record its next deadline and owner. If the operator expressly requests recurring/later follow-up, use only the host's supported scheduler and retain its actual ID. A go to work now is not permission to create a recurring automation. Active waits are not durable scheduling and no progress through app closure/sleep is promised. Never leave cadence to memory or lossy completion notifications. At each tick, re-read this installed playbook at its reviewed package identity, reconcile the operator's current limits, and audit the operation against it. Fix drift during that tick. Do not assume the recipient's trunk contains this plugin or replace reviewed instructions with unreviewed remote updates. Probe each owner with a generic liveness or status check using actual controls, and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once under delegation's lifecycle and resource rules. Do not wait for a polite return. The tick judges an owner by the pushed branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn. Each tick also runs the lane stuck test over the program's actual agent list, where the host exposes one, and over every owner's `children.tsv`. Whether or not a stop works, have the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. Before replacement writes resume, confirm the old writer/processes stopped or fence its checkout/resources; unknown control state blocks overlapping writes. Missing cancellation is a reported blocker, not a fictitious stop. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick only when no delegated work is left, even after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.

## Hold, interruption and recovery

On a stop/hold, relay zero-writes to every owner and child immediately through actual controls, inspect each returned state and owned processes, and record any unconfirmed stop. Keep branches, dirty work, trails and briefs; never delete a checkout as cancellation. A pause retains the selected mode and authority limits. Resume only after operator release and [artifact-first recovery](../references/continuation.md): inspect Git/forge state before replaying a push, retarget or merge, reconcile current heads with verdict receipts, recover the audit deadline, and confirm worker liveness rather than assume IDs survived. Replace dead/unknown workers with fresh consolidated briefs after containing surviving writers. Inspect an uncertain merge receipt before choosing the next item. Changed patches invalidate old findings/verdicts under Shipping's explicit rule; missing controls, CI, live verification, forge authorization or an enforced approval keep the affected item blocked, never clean by default. Continue independent authorized work and report exact gates.

Resolve the actual trunk branch/ref from repository configuration rather than assuming `main` or `origin/main`; substitute that verified ref in the full-mode drift checks. Read package references relative to this installed playbook, not the user's project tree. External verdict posts and customer/team messages obey host authorization. A countersign only covers the operator's delegated approval scope and can never bypass a forge-enforced approval.
