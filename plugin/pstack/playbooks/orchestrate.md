# Orchestrate

Before dispatch, read [native orchestration contract](../references/orchestration.md), [delegation](../references/delegation.md), [models](../references/models.md), [continuation/recovery](../references/continuation.md) and [PR delivery](../references/pr-delivery.md). These adapters govern execution and authority. This workflow expressly requests bounded local child delegation. Do not start until actual spawn, results, cancellation, filesystem and required forge capabilities are bound.


**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Bind native spawn/result/wait operations through [delegation](../references/delegation.md). Keep the program’s state in the discovered project tracker/store when supported; otherwise use the explicitly identified private `notes.md` and task store specified in [orchestration](../references/orchestration.md). Bind PR and CI event subscriptions only when actually exposed; record their absence rather than inventing an API. Call no scripts, run no polling loops, and never relay messages or status between agents.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Run workers in fresh isolated local Git worktrees with explicit cwd, base SHA and exclusive file/resource ownership. This replaces upstream cloud VMs; it is not a separate machine or security boundary. Reserve or serialize shared browsers, ports, simulators and authenticated sessions. Use the packaged [control-ui](../references/control-ui.md) or [control-cli](../references/control-cli.md) instructions for runtime checks when their required tools exist. Select each worker’s validated GPT model, reasoning effort and speed only where the actual host schema supports them, per [models](../references/models.md); otherwise inherit the parent defaults.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, capped by actual host capacity and safe local resources, and start the next one as each finishes instead of waiting on a whole batch.
- **Fork when new work needs a worker's built state,** such as its checkout, uncommitted changes, or a running process. Use a supported fork only if it preserves that state; otherwise retain the existing owner for same-work follow-up or hand off verified artifacts to a fresh isolated worker. Never assume a conversation fork clones processes or grants shared write ownership. Message a worker only for a follow-up on the same work. Never message one to check on it, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author,** using a distinct validated GPT model where available. Independent GPT contexts replace upstream cross-provider family diversity; disclose when the same model is reused and never call that provider diversity. The owner merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. Before a replacement writes, reconcile or contain the prior writer under delegation; interruption is not proof it stopped. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
